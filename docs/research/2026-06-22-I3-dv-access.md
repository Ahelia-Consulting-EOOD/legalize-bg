# I3 — Държавен вестник (ДВ) access + ЗИД parsing recon

**Date:** 2026-06-22. **Author:** I3 research agent (Claude Opus 4.8).
**Source log:** `2026-06-22-I3-dv-access-sources.md` (every claim traces to an `extract#N`).
**Scope:** RECON ONLY — characterize `dv.parliament.bg` structure/access for the Phase-3 poller + fetcher and the Phase-4 consolidation engine. 7 polite live requests made (all HTTP 200; no anti-bot challenge); no bulk crawling.

---

## 1. Issue structure (Брой / number + date; archive navigation; cadence)

ДВ is organized as a sequence of **issues** ("Брой"), each identified by an **issue number + publication date** (e.g. "Брой 56, 19.6.2026 г.") (extract#8, extract#13). The home page (`https://dv.parliament.bg/DVWeb/index.faces`) shows the latest issue (Брой 56, 19.6.2026 confirmed live) (extract#13).

**Archive navigation.** The canonical issue list is `https://dv.parliament.bg/DVWeb/broeveList.faces` (extract#5, extract#8). It is a JavaServer Faces (`.faces`) application: issues are listed **reverse-chronologically**, paginated at **413 pages across ~4,121 issues** (extract#8). A filter panel supports search by **keyword, issue number, type (all / regular / extraordinary), and a date-range picker** (extract#8). An older/alternate archive view `dv130.faces` also exists (extract#6). Each issue has an **"Изтегли броя"** ("download issue") action (extract#6, extract#13).

Two distinct ID spaces are in play (both confirmed live):
- **`materiali.faces?idObj=N`** — the *issue-contents* page listing every material in one issue (e.g. `idObj=6121` = Брой 46, 22.6.2026, 18 materials) (extract#11).
- **`showMaterialDV.jsp?idMat=N`** — one *individual document* within an issue (extract#9, extract#11, extract#13).

So `idObj` = issue, `idMat` = material/document. The contents page groups materials by official section: **Народно събрание** (Parliament — laws & ЗИД), **Министерски съвет** (Council of Ministers — постановления), **ministerial наредби/инструкции**, **regulatory-commission decisions**, **CEC decisions** (extract#11). This section grouping is the natural place a poller distinguishes a ЗИД (a parliamentary law) from a постановление or наредба.

**Cadence.** Regular issues publish **every Tuesday and Friday that are working days**; **extraordinary (извънреден) issues can appear on any day, including non-working days**, at the discretion of the NA Chairman (extract#15). This confirms the project's assumed Tue/Fri cadence — but the poller must NOT assume *only* Tue/Fri: извънреден issues are common (Брой 52, 8.6.2026 was извънреден) (extract#8) and carry binding amendments. **Poll on Tue/Fri as the baseline, but detect by latest-issue-number/date, not by calendar day.**

## 2. Document access (showMaterialDV.jsp?idMat=N; "Изтегли броя"; format)

**Primary readable surface = HTML text.** Every individual document fetched (`showMaterialDV.jsp?idMat=N`) renders as **server-side HTML text** — readable paragraphs with light markup (line breaks, bold), NOT an embedded PDF or scanned image (extract#9, extract#10). This is the same server-rendered-HTML world as lex.bg, so the existing `fetcher/bg/client.py` pattern transfers directly. **Encoding must be verified at fetch time** — lex.bg is cp1251; ДВ's encoding is unconfirmed in this recon and must be checked (look at the `Content-Type` charset / a `<meta charset>` and decode accordingly) before assuming UTF-8.

**The "Изтегли броя" PDF is the secondary/whole-issue surface.** Issues are downloadable as PDF (extract#6, extract#15), and `fileUploadShowing.jsp?idFileAtt=N&allowCache=true&openDirectly=false` serves file attachments (extract#1) — the mechanism for the whole-issue PDF and for normative-act **appendices** (which the gazette publishes only as online attachments, with the same legal force as print) (extract#15). The exact "Изтегли броя" href could not be cleanly extracted because the JSF link is JS/POST-driven (extract#13) — a detail for the implementation session, not a blocker.

**Recommendation:** consume the **per-document HTML** (`showMaterialDV.jsp?idMat=N`), enumerated from the **issue-contents** page (`materiali.faces?idObj=N`). This avoids PDF parsing entirely for the main text. The whole-issue PDF is a fallback for completeness/appendices; if a future appendix is a scanned image, per the global project rule it is read with **embedded vision (render + Read), never an external OCR library** — but the recon found the main act text is HTML, so OCR should rarely be needed.

**Note on JSF state.** `.faces` pages carry `jsessionid` and JSF `ViewState`; pagination/filtering on `broeveList.faces` is likely POST-driven, not a clean `?page=N` GET (extract#8). The poller should prefer the **stable GET surfaces** (`materiali.faces?idObj=N`, `showMaterialDV.jsp?idMat=N`) and treat the JSF list as a discovery seed (find the latest `idObj`), rather than trying to crawl all 413 list pages.

## 3. ЗИД cross-references — THE KEY QUESTION (definitive answer)

**DEFINITIVE: ДВ does NOT expose ЗИД→amended-act linkage as structured/machine-readable data. The amended act must be PARSED from the ЗИД title prose.** Confirmed across three independent documents:

- A real ЗИД (`idMat=147391`): the amended act appears **only in the document title** — "Закон за изменение и допълнение на **Закона за мерките и действията по време на извънредното положение**, обявено с решение на Народното събрание от 13 март 2020 г." — with **no "history of document" section, no hyperlink, and no consolidated-law reference** anywhere on the page (extract#9).
- An амендиращ instrument of a different type (`idMat=17529`, an Инструкция): "**No hyperlinks** to amended legislation exist"; laws are referenced **only through inline prose citations** of the form **"(ДВ, бр. N от YYYY г.)"** (extract#10).
- N-Lex (the EU gateway) independently confirms ДВ "consists mainly of **editions and corrections** of official documents, and **not of the full texts** of actual laws," and provides **only a search form, no API and no cross-reference graph** (extract#12).

**What the project doc calls `.HistoryOfDocument` is an APIS construct, NOT a ДВ feature.** APIS (the commercial consolidator, `web.apis.bg` — and the layer behind lex.bg-class providers) *builds its own* family graph: it "track[s] documents that amend ('**Изменя**') preceding acts and documents that are amended by ('**Изменен със**') subsequent amending acts" (extract#7). That linkage is value APIS adds on top of the raw gazette — it is exactly the relationship our pipeline must reconstruct itself, and exactly the kind of derived compilation that motivates the FR-024/D-038 provenance concern about reusing a private consolidator's DB.

**Implication for the Phase-3 amendment detector.** The detector must:
1. Enumerate an issue's materials (`materiali.faces?idObj=N`), keep the **Народно събрание** laws.
2. Match the title against the ЗНА-prescribed ЗИД template: `^Закон за изменение(?: и допълнение)? на (Закона|Кодекса|...) за …`. The grammatical genitive ("**на Закона за …**") names the target.
3. **Resolve the title to a corpus act.** This is the hard part — the title carries a *declined* (genitive) act name, not our stored nominative `titulo`/`identificador`. The matcher must normalize case/declension (reuse the existing `bg_normalize` / Cyrillic-casefold work from FR-019) and fuzzy-match to a corpus act.
4. **Disambiguate with the inline `(ДВ, бр. N от YYYY г.)` citation** — the one semi-structured anchor ДВ provides. It cites the issue where the *amended* act was originally promulgated, which can be cross-checked against the corpus act's `amendment_history`/`fecha_publicacion`/`Source-Id` to confirm the target when titles collide. Likewise `[popravka]` (поправка) and `[otmyana]` (отмяна/repeal) instruments name their target the same prose way.

**Net:** linkage is *parse-not-fetch*, but ДВ's prose is regular (ЗНА-templated title + `(ДВ, бр. N от YYYY)` citation), so a deterministic title parser + a declension-aware corpus matcher is feasible; ambiguous titles are flagged for LLM-assisted/manual resolution (consistent with the deterministic-or-flagged Phase-4 posture).

## 4. Structured datasets (data.egov.bg; any official ДВ API/feed)

**No official structured ДВ dataset, API, or feed exists.** Findings:
- `dv.parliament.bg` itself: no API, no XML/JSON endpoint, no RSS/Atom feed surfaced; it is a JSF web app over a search form (extract#2, extract#8). No `robots.txt` and no sitemap published (extract#14).
- `data.egov.bg` (the national open-data CKAN portal): no ДВ dataset identified; the portal exists and is machine-readable in principle, but the gazette is not published there as a reusable dataset (extract#3).
- **N-Lex** (`n-lex.europa.eu`, the EU "common gateway to national law"): points to dv.parliament.bg as the official source but offers **only a search form front-end, no API, no programmatic access**, and explicitly **no free consolidated full texts** (extract#12). Its Bulgarian search form is APIS-backed (the `legis_bg/apis_form` path), reinforcing that the structured/consolidated layer is the commercial providers (APIS / Сиела / lex.bg), not the state.

**Conclusion (grounds the roadmap's central premise):** Bulgaria has **no official consolidated-law API and no structured gazette feed**. ДВ is the authoritative *primary* source but ships only raw issue text. This is exactly why the ecosystem's "fetch official consolidated text from a government API" path (Spain BOE, France Légifrance, EU Cellar) is unavailable here, and why self-consolidation from ДВ (Phase 4) with lex.bg-as-validation-oracle is the only sovereign path. (Cross-confirms I4.)

## 5. Access politeness (robots.txt / ToS; recommended polite-access approach)

- **No `robots.txt`** is published at the dv.parliament.bg root (HTTP 404) (extract#14) — there is no machine-readable crawl policy, neither permitting nor forbidding. Absence of robots.txt is not license to hammer; the polite default still applies.
- **No Cloudflare / anti-bot challenge** was encountered across the 7 live recon requests — the site served plain HTML on every GET (extract#8–#13). The existing `is_cloudflare_challenge()` halt-on-challenge guard should still be wired in defensively.
- ДВ is an **official state publication with free public access** (extract#15, extract#12); the act **texts are public-domain** under ЗАПСП чл. 4 (state-of-emergency: official texts of state bodies are not protected) — consistent with the project's D-039 posture. There is no APIS-style чл. 93б database-right problem with ДВ itself (the database-right concern is specific to the commercial consolidators' *compilations*, not the gazette's raw issues).

**Recommended polite-access approach (mirror the lex.bg protocol):**
1. **Reuse `fetcher/bg/client.py:RateLimitedSession`** — ≤ **1 request/second**, exponential backoff (2/4/8 s) on 429/5xx, halt-on-Cloudflare. Add ДВ as a second host/transport sharing the same global rate ceiling.
2. **Descriptive User-Agent** — extend the existing `legalize-bg/0.1 (…github…)` UA (NOT a browser string).
3. **Poller is cheap by design.** Steady-state freshness = a few GETs twice a week (latest issue list → new `idObj` → its materials), not a crawl. No bulk download.
4. **Verify charset at fetch** (do not assume cp1251 *or* UTF-8 — confirm per response; §2).
5. **Log every request** (URL, status, ms) per the contract's Rule 5.

## Recommended access design for Phase 3 (DV monitor / FR-002)

**Discovery → enumerate → classify → resolve → flag**, all over stable GET surfaces:

1. **Detect new issues** — on the Tue/Fri baseline (plus a daily light check for извънреден), read the latest-issue marker (`index.faces` / top of `broeveList.faces`) and compare the latest **Брой number + date** against a persisted high-water mark. Issue numbers are monotonic within a year, so a simple `(year, number)` cursor detects gaps. Avoid crawling the 413-page JSF list — only walk back far enough to cover any missed issues.
2. **Enumerate materials** — for each new issue, GET `materiali.faces?idObj=N` and parse the per-material `showMaterialDV.jsp?idMat=M` links, retaining the **section** (Народно събрание vs МС vs наредби) (extract#11).
3. **Fetch + classify each material** — GET the HTML; classify by title template into `[reforma]` (ЗИД), `[nova]` (new law), `[otmyana]` (repeal), `[popravka]` (corrigendum), or non-corpus (resolutions/appointments).
4. **Resolve target act** — for amending instruments, parse the genitive act name from the title + the inline `(ДВ, бр. N от YYYY)` citation; declension-aware match to a corpus act (reuse FR-019 Cyrillic-casefold); disambiguate via `amendment_history`/`Source-Id`. Unresolved/ambiguous → flag.
5. **Alert/log** — record `(idObj, idMat, issue, date, target_law_id?, op_type, confidence)` for Phase-4 consolidation; flagged items go to a review queue. This satisfies the Phase-3 DoD (poller + amendment detector + alert/log) without yet applying any change.

Phase 4 then consumes the **HTML ЗИД text** (already fetched) as the deterministic operation stream; lex.bg stays the byte-validation oracle (D-003/D-b).

## Open risks

- **R1 — Title→act resolution accuracy.** The only linkage is declined prose + a `(ДВ, бр. N)` citation; collisions (e.g. multiple acts with similar names, or codices vs their implementing laws) need the citation cross-check and a flag-on-ambiguity path. Coverage is unmeasured until built (parallels handoff T2). **Highest-effort Phase-3 risk.**
- **R2 — JSF/`ViewState`/`jsessionid` fragility.** Pagination and filtering on `broeveList.faces` are POST/stateful (extract#8); the design deliberately leans on the stable GET surfaces (`materiali.faces?idObj=N`, `showMaterialDV.jsp?idMat=N`) and a monotonic issue cursor to avoid driving the JSF list machine. The `idObj`↔issue and `idMat`↔document mapping must be learned empirically (the two ID spaces are independent and not obviously sequential).
- **R3 — Encoding unconfirmed.** ДВ charset not verified this recon; must be detected per-response (cp1251 vs UTF-8) before decoding (§2).
- **R4 — Извънреден issues off-cadence.** Binding amendments can land on any day (extract#8); a strict Tue/Fri-only poller would miss them. Mitigation: poll by latest-issue-number, with a lightweight daily check.
- **R5 — Whole-issue PDF / appendices.** If a normative act's appendix is published only as a PDF attachment (`fileUploadShowing.jsp?idFileAtt=N`) and is a scanned image, extraction uses embedded vision per the global rule (no external OCR). The main act text is HTML, so this is an edge case, not the common path.
- **R6 — No robots.txt / ToS ambiguity.** No published crawl policy (extract#14); proceed on the official-publication + public-domain-text basis (§5) with strict ≤1 req/s politeness, and halt-on-challenge defensively.
