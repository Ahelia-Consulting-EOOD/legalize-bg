## Q1 — What is LawVM? (replay-compiler concept + instruction set)

LawVM is **"a deterministic replay compiler for legislation"** that **"reconstructs point-in-time statutory text from amendment streams"**, treating **"human-written amendment law as already executable"** — it compiles **"the amendment stream already published by the legal system rather than relying on editorial consolidations"** [extract#1]. The one-line theory: **"LawVM = compiler from hostile legislative deltas to a proof-carrying temporal legal-state machine"** [extract#16]. The compiled product is **"time-indexed legal state"** built from **"amendment deltas applied forward through time"** [extract#16].

**Why this is possible (the "law-shaped" argument — general theory, LawVM-articulated):** law is **"an incrementally maintained system authored by distributed agents"** that requires **"stable fine-grained addresses for external reference"**; because provisions reference each other ("pursuant to Section 12(2)"), **"amendments must operate deterministically on a versioned substrate"** — law behaves like version-controlled software [extract#3]. Amendment acts already phrase themselves as instructions: *"Section 12, subsection 2 is amended to read as follows"* encodes instruction semantics, not narrative prose [extract#4].

**The instruction set (typed operations).** An amendment is modelled as a **typed operation** with four components: **target address, action type, payload, and source provenance** [extract#4]. The repo README enumerates the verbs the system mutates a statute tree with: **"replace, repeal, insert, renumber, move, delay commencement, restrict scope"** [extract#7]. The formal, *normatively-specified* canonical kernel (in `CANONICAL_OP_SEMANTICS.md`) is deliberately **small and "semantics-poor"** [extract#16] — currently four ops with explicit pre/postconditions [extract#8]:

- **`replace`** — replace the content at the target address with the provided payload (arg: target address + explicit IR subtree payload; precond: target must have a substantive or tombstone/scaffold occupant; postcond: emits a new version, must not duplicate siblings).
- **`insert`** — add a new provision/child provision at the target address (precond: exact slot absent OR occupied by a non-substantive scaffold/tombstone; postcond: insertion ordering deterministic, consumes the non-substantive occupant).
- **`repeal`** — the targeted provision ceases to be in force as a substantive node (payload `None`, tombstone-style; postcond: structural removal OR tombstone replacement per jurisdiction policy).
- **`text_replace`** — a *constrained* textual correction on an already-targeted subtree, **"explicitly kept narrow; not a generic text editor"** [extract#8].

Crucially, **`renumber`/`move` are deferred as "future families … only when semantics are explicit"** [extract#8] — i.e. the project does NOT yet treat renumbering as a primitive replay op; it is handled upstream (see Q5). This is a deliberate discipline: keep the replay kernel tiny and total, push ambiguity to a separate layer.

**The pipeline.** LawVM is a multi-phase compiler. The home-page short form: **"amendment act → parse → typed ops → resolve targets → replay → PIT state → compare → classify"** [extract#2]. The README's full 10 phases [extract#7]: (1) acquire+archive source artifacts; (2) parse the operative source surface; (3) derive clause/effect surfaces; (4) extract+normalize payload shape; (5) **elaborate** targets against live legal state; (6) **lower** to canonical typed operations/effects; (7) **replay** over a statute tree; (8) compile timelines + **materialize** point-in-time law; (9) **adjudicate** replay against witness/oracle surfaces; (10) emit evidence, findings, unresolved states. The key architectural separation: **"lowering, target resolution, replay, and divergence accounting"** are separate **"so that mismatches are inspectable rather than collapsed into a single opaque failure state"** [extract#5]. The first stable representation is a **"clause surface" = "a typed AST for amendment instruction language"** [extract#5].

## Q2 — Locators / addressing (how operations are precisely located)

This is the part most directly load-bearing for deterministic replay, and LawVM is precise about it.

**Address format.** A provision is identified by a canonical **`LegalAddress`** string: **slash-joined `kind:label` segments**, e.g. `section:6a` or `chapter:4a/section:30a`. The string **"MUST NOT contain whitespace around segment separators, kind names, or labels"** [extract#10]. This is path-based addressing; the theory page notes the same convergence appears in OIDs, Xanadu tumblers, ELI, FRBR, and filesystems — all solving hierarchical addressing under distributed modification [extract#4].

**Target resolution (the determinism guarantee at the locator level).** Resolution is **"exact-match first, then unique-suffix match."** If two or more suffix matches exist, the system does NOT guess — it yields **`ambiguous_address` with sorted `address_candidates`** [extract#10]. Strict mode **"forbids target guessing, hidden insertion anchoring, fallback replacement, ambiguous omission expansion, silent date estimation"** [extract#5]. So a locator that cannot be resolved uniquely becomes an explicit flagged fact, never a silent best-guess.

**Provision state (so ops can have preconditions on the target).** Each version carries a **`content_state`**: `"live"` (substantive text), `"tombstone"` (content `None`, repealed-to-placeholder), or `"absent"` (address resolved but no version active at `as_of`) [extract#10]. This is what lets `insert` require an absent/non-substantive slot and `repeal` require a substantive occupant [extract#8].

**Identity across renumbering.** Node identity is decoupled from positional label. A **`lineage`** field `{status, address_chain, migration_event_count_considered, fingerprint…}` carries an **`address_chain` that "traces renumbering/migration history considered at `as_of`"** — a stable identity anchor independent of positional labels [extract#10]. Renumber is "an explicit operation because addresses are positional; renumbering is recorded to update external references" [extract#4]. (Note the tension with Q1: the *theory*/README treat renumber as an operation, but the *normative kernel* still defers it — see Q5.)

**Parsing the locator from amendment prose.** The Finnish frontend parses targets out of the enacting clause (johtolause): section `muutetaan 12 §` (with ranges `3, 5 ja 7 §` and suffixed `5 a §`), chapter scope `kumotaan 3 luku` / `muutetaan 3 luvun 12 §:n 2 momentti`, and sub-references `momentti` (paragraph), `kohta` (clause), `otsikko` (heading), `johdantokappale` (preamble) [extract#13]. This maps almost one-to-one onto Bulgarian addressing (чл./ал./т./раздел/глава) — see Q5.

## Q3 — Validation & divergence reporting (hard-fail, never silent accept)

This is the property the owner explicitly wants, and LawVM's failure model is the strongest part of the design for our purposes.

**Two-level validation.** (a) *Internal* replay invariants checked during replay, and (b) *external* adjudication of the materialized PIT text against the oracle/witness surface.

**(a) Replay invariants & failure model** [extract#9]. Named invariants must hold, e.g. `REPLAY_APPLY_ACCOUNTING_BASIC` ("a successful op reports one clear semantic target … **a failed op is a no-op**"), `REPLAY_DUPLICATE_SIBLING_LABEL`, `REPLAY_PLACEHOLDER_STATE_CONTRADICTION` ("a provision cannot be simultaneously a repeal placeholder and substantive content"). **Strict-mode HARD FAILURES** include: `REPLAY_DUPLICATE_SIBLING_LABEL`, `REPLAY_SKIPPED_OP_MUTATED_TREE`, `REPLAY_FAILED_OP_MUTATED_TREE`, `REPLAY_MISSING_PRIMARY_TARGET_CONSUMPTION`, `REPLAY_APPLY_BOUNDARY_TOUCH_OUTSIDE_TARGET`, `REPLAY_MULTIPLE_PRIMARY_TARGET_CONSUMPTIONS`, `REPLAY_PLACEHOLDER_STATE_CONTRADICTION`, `REPLAY_PLACEHOLDER_ADDRESS_SHADOW`. Below that, **warnings** (non-fatal, recovery-sensitive): duplicate text/tract, broad-clobber residue, undeclared secondary touches, unexpected scaffold consumption. Governing principle: **"Replay should execute canonical meaning and report what it actually touched. It should not perform opaque tree surgery"** — every mutation is an explicit `ApplyMutationEvent` so causality stays known [extract#9]. The whole-system rule: **"divergence is never silently accepted"; "every nontrivial recovery or failure must become an explicit fact"** [extract#16]. This is precisely the owner's "hard-fail / flag, never silent 70-90% accept" bar.

**(b) Adjudication against the oracle.** The oracle is a **witness, not automatic truth**: **"the 'oracle' is not always authoritative. Consolidated legal text may be stale, editorially annotated, or otherwise non-commensurable with the true PIT state"** [extract#16]; CLI surfaces are **"evidence, not automatic truth"** [extract#7]. Divergence between replayed PIT text and the oracle is sorted into **four lanes** [extract#12]: **Source Pathology Lane** (defects/underdetermination in the published source itself), **Replay Demotion Lane** (facts that defeat replay attribution without proving source pathology — e.g. preexisting divergence), **Risk Signal Lane** (suspicion indicators that don't by themselves prove cause), **Editorial Lane** (editorial metadata in the consolidated artifact, e.g. inline repeal stubs). To decide *LawVM-bug vs official-consolidation-bug*, it runs an **editorial-witness cross-check**: `editorial_witness_confirmed` (consolidation's stub amendment-ID matches the compiled timeline), `editorial_witness_disagrees` ("requires manual triage; either editorial error or replay bug"), `editorial_witness_unresolved` (stub claims a repeal with no timeline terminator → risk signal) [extract#12].

**Finland numbers (what the case demonstrated)** [extract#6]: **690 fully-replayable amended statutes** spanning the 1920s–2020s (107 from the 1990s, 173 from the 2000s, 237 from the 2010s, 118 from the 2020s). Against an archived Finlex consolidation (frozen 2026-04-16, mode `finlex_oracle`): **mean Levenshtein text distance 0.65%**, **mean section-level structural error 4.25%**, **367 perfect structural matches**, **490 statutes at ≥95% agreement**, **104 below 90%** (the "investigation frontier"). It produced **22 candidate divergence findings reported to Finlex** (ticket RITM0644009, 2026-04-23), root-caused as: missing content 10, source pathology 9, missing section headings ≥9, stale cutoff ≥6, editorial addition 4, coverage gaps 3, dual-element residual 3, misapplied correction 1. The home page also cites a confirmed correction in Estonia's Auditors Activities Act [extract#2]. **Read for Bulgaria:** even a mature deterministic compiler does NOT hit 100% byte-match against the official surface — and that is the *point*: the residual gap is the finding, attributed to a lane, not silently absorbed. Comparison surface = official consolidated text vs **raw amendment acts in the gazette XML (Säädöskokoelma)** [extract#6].

## Q4 — Forward replay vs reverse-apply (confirmation + FR-009 implication)

**Confirmed: LawVM is forward replay.** Consolidation "represents the cumulative effect of the amendment stream," produced by **"amendment deltas applied forward through time"** [extract#16], with replay **"forward-moving through time, applying only active events at each step"** [extract#15]. The pipeline anchors on acquired primary source artifacts and replays **over a base/statute tree** in order [extract#5, extract#7]. It never "undoes" the current consolidated text backward.

**Ordering rule (load-bearing for our git-dated commits).** Amendments are ordered for replay by: **effective (in-force) date primary, then enacted/publication date, then source sequence, then structural specificity** [extract#15]. Time is modelled **bitemporally + an optional third axis**: *Enactment/Publication Time*, *Legal Effect Time* (in-force), and optional *Observation Time* (for reproducibility) [extract#15]. A subtlety to carry into our design: **effect time is "either a resolved date, or a trigger rule awaiting resolution"** [extract#15] — i.e. some provisions enter force conditionally, not on a fixed date.

**Implication for FR-009.** This validates the handoff §3a reframe: FR-009's old "reverse-apply" wording should become **forward replay** — anchor on the **ДВ original promulgation** (sovereign source), fetch each later ЗИД's text from ДВ, replay forward in ДВ-date order, and use lex.bg only as the **validation endpoint** (the witness/oracle). This is also the property that retires lex.bg from the *source* role while keeping it as the *oracle* (project D-b). Note LawVM orders by *effective* date first, not publication date — Bulgarian ЗИД typically state влизане в сила separately from the ДВ publication date, so our ordering must read the in-force date, not just the ДВ issue date, and model deferred/conditional commencement.

## Q5 — Applicability to Bulgarian ЗИД (what transfers; hard cases)

**Direct structural fit.** Bulgarian legislative drafting (prescribed by ЗНА + Указ 883) is as formulaic as Finnish, and the project's design doc already anticipates a near-identical operation taxonomy [extract#11]. The Finnish enacting-clause verbs map cleanly to Bulgarian:

- `kumotaan` (repeal) ↔ **отменя се** → `repeal`
- `muutetaan` (amend) ↔ **се изменя / думите „…" се заменят с „…"** → `replace` or `text_replace`
- `lisätään` (insert) ↔ **се създава (нов чл./ал./т.)** → `insert`

Bulgarian addressing (чл. X, ал. Y, т. Z, раздел, глава, with lettered suffixes like чл. 5а) maps directly onto the `LegalAddress` `kind:label` path model and onto the Finnish `12 §:n 2 momentti / 5 a §` parse [extract#10, extract#13]. So the **clause-surface AST + canonical `replace`/`insert`/`repeal`/`text_replace` kernel transfers as-is**, and the project's existing taxonomy (substitution ~40%, addition ~25%, deletion ~15%) lowers onto it.

**The single biggest lesson:** LawVM's difficulty is NOT in the replay kernel — once canonical ops exist, **"replay is comparatively boring."** The hard work lives in the **ELABORATION layer** (phase 5): turning surface amendment prose into canonical ops *against the live legal state* [extract#14]. This reframes the whole engine effort for us: the deterministic core is small; the investment is the BG-specific elaboration frontend.

**Known hard cases the design MUST handle** [extract#14, extract#13]:
- **Renumbering** — "subsection/item recovery when source coordinates are incomplete." LawVM keeps renumber OUT of the replay kernel [extract#8] and handles cascade in elaboration; BG's `jolloin`-equivalent is the explicit *"като досегашните чл. X-Y стават чл. …"* / *"номерацията се променя съответно"* phrasing. Identity is preserved via the `lineage`/`address_chain`, not the label [extract#10].
- **Restructuring (move/split/merge)** — "broad-target to narrow-target rewrites"; live-state dependent, resolved in elaboration.
- **Tables / annexes (приложения, тарифи)** — "tables flattened into subsection-looking structures," needing "table-row reconciliation against the actual live tree." Grammar alone fails; the project's taxonomy already flags Table/annex as ~1% "manual" [extract#11].
- **Conditional / deferred commencement (влизане в сила)** — "temporary-law and commencement interactions" that "change meaning over time"; model effect-time as a date-or-trigger-rule [extract#15].
- **Ambiguous/broad targets** — the johtolause names `1 §` but the body changes only a few rows; "legal meaning is frequently split across three places" [extract#14]. Resolve via exact-then-unique-suffix matching with loud `ambiguous_address` failure [extract#10].

**What transfers vs what we build.** Transfers: the *model* (forward replay, typed-op kernel, LegalAddress, content_state, lineage, witness-not-truth oracle, invariant-based hard-fail, divergence lanes). We build (BG-owned, per D-039): the BG elaboration frontend (ЗИД johtolause-equivalent grammar over ЗНА phrasing), the ДВ acquisition layer (I3), and the lex.bg adjudication adapter (oracle witness). We must NOT reuse any LawVM code blindly as authority — it is research software [extract#1] — but the spec corpus is an excellent design template.

## What transfers to Bulgarian ЗИД

1. **Adopt forward replay, not reverse-apply.** Anchor on ДВ original promulgation; replay each ЗИД forward; this is what retires lex.bg as *source* while keeping it as *oracle* (fixes FR-009 wording; matches handoff §3a, D-b). Order by **in-force date then ДВ publication date**; model deferred/conditional влизане в сила as date-or-trigger [extract#15, extract#16].

2. **Keep the replay kernel tiny and total.** Start with the four normative ops (`replace`, `insert`, `repeal`, `text_replace`); keep `renumber`/`move`/restructuring in a separate **elaboration** layer. The deterministic core is small; the BG-specific *elaboration grammar* is where the effort goes ("replay is comparatively boring") [extract#8, extract#14].

3. **Use a canonical `LegalAddress` (`kind:label` path) with exact-then-unique-suffix resolution that fails loudly.** чл./ал./т./раздел/глава + lettered suffixes (чл. 5а). Carry `content_state` (live/tombstone/absent) and a `lineage`/`address_chain` so renumbering preserves node identity [extract#10].

4. **Make the failure model the gate, not an accuracy %.** Replace the delivery-contract "≥70%/≥90%" (handoff D-a) with: replay invariants as **hard failures** (failed op = no-op; no op touches outside its target; no opaque tree surgery), plus oracle **adjudication** into divergence lanes (source-pathology / replay-demotion / risk-signal / editorial) with an **editorial-witness cross-check** to attribute LawVM-bug vs lex.bg-bug. **"Divergence is never silently accepted"** [extract#9, extract#12, extract#16].

5. **Treat lex.bg as a witness, not truth** (matches D-003/D-b): expect a residual byte-gap (Finland: 0.65% text / 4.25% structural; 104/690 below 90%), and classify it rather than absorb it. The official surface can itself be wrong — the compiler is an independent oracle that *finds* consolidation bugs [extract#1, extract#6].

6. **Plan for the known hard cases up front** (renumbering cascades, restructuring, tables/annexes/приложения, conditional commencement, broad/ambiguous targets) — all live in elaboration, all are where LLM-*assist* may propose ops, but the **deterministic validation gate (invariants + oracle adjudication) is the authority**, never an LLM confidence score [extract#14].
