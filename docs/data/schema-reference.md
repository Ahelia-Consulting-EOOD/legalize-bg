# Schema Reference

Technical reference for all structured data schemas in legalize-bg. Two schemas govern the system: YAML frontmatter (embedded in each Markdown file) and SQLite tables (derived index for temporal queries).

---

## Section 1: YAML Frontmatter Schema

Every Markdown file in the repository begins with a YAML frontmatter block delimited by `---`. The frontmatter contains 13 fields (8 mandatory Legalize SPEC fields + 5 Bulgarian extensions) plus an `amendment_history` array.

### Example

```yaml
---
titulo: "Закон за обществените поръчки"
identificador: "2136735703"
pais: bg
rango: закон
fecha_publicacion: "2016-02-16"
ultima_actualizacion: "2024-03-15"
estado: vigente
fuente: "lex.bg"
dv_issue: "13"
dv_year: 2016
effective_date: "2016-04-15"
category: laws
eli: "/eli/bg/закон/2016/2/16/zop/con"
amendment_history:
  - dv: "34/2016"
    date: "2016-05-03"
  - dv: "63/2017"
    date: "2017-08-04"
---
```

### Mandatory Legalize Fields (8)

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| `titulo` | string | Required. Non-empty. | Full official title of the normative act in Bulgarian. |
| `identificador` | string | Required. Numeric string matching lex.bg doc ID. | Unique document identifier from lex.bg (e.g., "2136735703"). Used to construct the source URL: `https://lex.bg/laws/ldoc/{identificador}`. |
| `pais` | literal | Required. Must be `bg`. | ISO country code. Always "bg" for this repository. |
| `rango` | enum | Required. One of: `закон`, `кодекс`, `наредба`, `правилник`, `правилник по прилагане`. | Legal rank/type of the normative act in the Bulgarian hierarchy. Values are in Bulgarian to match the Legalize convention of using the country's own legal terminology. |
| `fecha_publicacion` | date | Required. ISO 8601 format (YYYY-MM-DD). | Date the act was first published in the State Gazette (Държавен вестник). |
| `ultima_actualizacion` | date | Required. ISO 8601 format (YYYY-MM-DD). | Date of the most recent amendment's publication in DV. Equals `fecha_publicacion` if the act has never been amended. |
| `estado` | enum | Required. One of: `vigente`, `derogado`. | Current status. `vigente` = in force; `derogado` = repealed. |
| `fuente` | literal | Required. Must be `lex.bg`. | Data source used for bootstrapping. May change to `dv.parliament.bg` for acts tracked via the DV monitor pipeline. |

### Bulgarian Extension Fields (5)

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| `dv_issue` | string | Required. Numeric string. | Issue number of the DV in which the act was first published (e.g., "13"). |
| `dv_year` | integer | Required. Four-digit year. | Year of the DV issue in which the act was first published (e.g., 2016). |
| `effective_date` | date | Required. ISO 8601 format (YYYY-MM-DD). | Date the act entered into force. Often differs from `fecha_publicacion` — Bulgarian law commonly specifies a grace period (e.g., "в сила от 15.04.2016 г." for an act published 2016-02-16). |
| `category` | enum | Required. One of: `laws`, `codes`, `ordinances`, `regulations`, `implementing`. | Repository directory category. Determines which top-level folder the file lives in. |
| `eli` | string | Required. URI pattern: `/eli/bg/{rango}/{year}/{month}/{day}/{slug}/con`. | Constructed European Legislation Identifier. Bulgaria does not officially assign ELI URIs, so these are generated by the pipeline following the ELI standard pattern. |

### Amendment History Array

| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| `amendment_history` | array | Optional. Empty array if no amendments. | Ordered list of all amendments applied to the act, from earliest to most recent. |
| `amendment_history[].dv` | string | Required within element. Format: `{issue}/{year}`. | DV issue reference for the amendment (e.g., "63/2017"). |
| `amendment_history[].date` | date | Required within element. ISO 8601. | Publication date of the amending DV issue. |

## Section 2: SQLite Schema

The SQLite database is a derived index — it is fully reconstructible from git history and YAML frontmatter. It accelerates temporal queries, full-text search, and cross-law amendment lookups.

### Table: `laws`

Master registry of all normative acts in the repository.

```sql
CREATE TABLE laws (
    law_id TEXT PRIMARY KEY,
    doc_id INTEGER,
    title TEXT NOT NULL,
    category TEXT NOT NULL,
    status TEXT DEFAULT 'vigente',
    current_commit TEXT
);
```

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `law_id` | TEXT | PRIMARY KEY | Short slug identifier (e.g., "zop", "zeu", "npk"). Matches the filename without extension. |
| `doc_id` | INTEGER | Unique, nullable | lex.bg numeric document ID (e.g., 2136735703). NULL for acts not sourced from lex.bg (future municipal acts). |
| `title` | TEXT | NOT NULL | Full official title in Bulgarian. Mirrors `titulo` from YAML frontmatter. |
| `category` | TEXT | NOT NULL | One of: laws, codes, ordinances, regulations, implementing. Mirrors `category` from YAML frontmatter. |
| `status` | TEXT | DEFAULT 'vigente' | Current status: "vigente" (in force) or "derogado" (repealed). Mirrors `estado` from YAML frontmatter. |
| `current_commit` | TEXT | Nullable | Git commit hash of the HEAD version for this file. Updated on every commit that modifies the file. |

### Table: `law_versions`

Temporal version index. Each row represents one version of an act — a specific text that was in force during a date range.

```sql
CREATE TABLE law_versions (
    id INTEGER PRIMARY KEY,
    law_id TEXT REFERENCES laws(law_id),
    valid_from DATE NOT NULL,
    valid_to DATE,
    commit_hash TEXT NOT NULL,
    dv_issue TEXT,
    dv_date DATE,
    amending_act TEXT
);
```

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | INTEGER | PRIMARY KEY, autoincrement | Surrogate key. |
| `law_id` | TEXT | FOREIGN KEY → laws(law_id) | Which act this version belongs to. |
| `valid_from` | DATE | NOT NULL | Effective date of this version (when the amendment entered into force). |
| `valid_to` | DATE | Nullable | Last date this version was in force. NULL means this is the current version. |
| `commit_hash` | TEXT | NOT NULL | Git commit hash that created this version. Use `git show {commit_hash}:{path}` to retrieve the text. |
| `dv_issue` | TEXT | Nullable | DV reference for the amendment that created this version (e.g., "63/2017"). NULL for bootstrap versions. |
| `dv_date` | DATE | Nullable | Publication date of the amending DV issue. |
| `amending_act` | TEXT | Nullable | Name of the amending act (e.g., "ЗИД на ЗОП"). NULL for bootstrap versions. |

### Table: `amendments`

Individual amendment operations. One ЗИД may produce multiple rows — one per discrete change operation.

```sql
CREATE TABLE amendments (
    id INTEGER PRIMARY KEY,
    source_act TEXT NOT NULL,
    target_law TEXT REFERENCES laws(law_id),
    operation TEXT NOT NULL,
    affected_articles TEXT,
    dv_issue TEXT,
    dv_date DATE
);
```

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | INTEGER | PRIMARY KEY, autoincrement | Surrogate key. |
| `source_act` | TEXT | NOT NULL | The amending act — the ЗИД or ПЗР that enacted this change (e.g., "ЗИД на ЗОП, ДВ бр. 63/2017"). |
| `target_law` | TEXT | FOREIGN KEY → laws(law_id) | The act being amended. A single source_act may target multiple laws (via ПЗР cross-law amendments). |
| `operation` | TEXT | NOT NULL | Operation type: substitution, addition, deletion, repeal, restructure, renumbering, new_chapter, table_annex. |
| `affected_articles` | TEXT | Nullable | Semicolon-delimited list of affected provisions (e.g., "чл. 14, ал. 1; чл. 20, ал. 1"). |
| `dv_issue` | TEXT | Nullable | DV issue reference (e.g., "63/2017"). |
| `dv_date` | DATE | Nullable | Publication date of the DV issue. |

### Table: `provisions`

Per-provision temporal index. Tracks the lifecycle of individual articles and paragraphs across amendments.

```sql
CREATE TABLE provisions (
    id INTEGER PRIMARY KEY,
    law_id TEXT REFERENCES laws(law_id),
    article TEXT NOT NULL,
    paragraph TEXT,
    valid_from DATE NOT NULL,
    valid_to DATE,
    text_hash TEXT
);
```

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | INTEGER | PRIMARY KEY, autoincrement | Surrogate key. |
| `law_id` | TEXT | FOREIGN KEY → laws(law_id) | Which act this provision belongs to. |
| `article` | TEXT | NOT NULL | Article number, including suffixes (e.g., "1", "14а", "115б"). |
| `paragraph` | TEXT | Nullable | Paragraph number within the article (e.g., "1", "2"). NULL if the provision is the entire article. |
| `valid_from` | DATE | NOT NULL | Date this provision version entered into force. |
| `valid_to` | DATE | Nullable | Last date this provision version was in force. NULL means currently in force. |
| `text_hash` | TEXT | Nullable | SHA-256 hash of the provision's text content. Used for change detection — if the hash changes between versions, the text was amended. |

### Indexes

```sql
CREATE INDEX idx_versions_date ON law_versions(law_id, valid_from);
CREATE INDEX idx_amendments_target ON amendments(target_law, dv_date);
CREATE INDEX idx_provisions_article ON provisions(law_id, article, valid_from);
```

| Index | Columns | Purpose |
|-------|---------|---------|
| `idx_versions_date` | `law_versions(law_id, valid_from)` | Accelerates "what version of law X was in force on date Y?" queries. The most common temporal lookup. |
| `idx_amendments_target` | `amendments(target_law, dv_date)` | Accelerates "what amendments were applied to law X, ordered by date?" and period-range queries. |
| `idx_provisions_article` | `provisions(law_id, article, valid_from)` | Accelerates per-article lookups: "show me the history of чл. 14 of ЗОП." |
