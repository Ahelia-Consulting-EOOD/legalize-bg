| FR-012 | Article body — preamble-stripped projection for amendment detection | 4 | Medium | Backlog | Phase 1b.1's `index.provisions.parse()` emits each article's body as the **entire markdown paragraph** (title preamble + "Чл. N." anchor + alinea text) — correct for Phase 1b.1's `get_article` and FTS use cases, where preserving context helps callers and ranking. Phase 4 amendment-detection regexes need a separate `body_text_minus_preamble` projection that strips the leading title preamble and the anchor itself, so substitution/addition/deletion patterns match unambiguously against alinea text. Either add a new column `provisions.body_clean` via migration or compute on demand from `text`. Keep `text` unchanged to preserve Phase 1b.1 contract. |
| FR-013 | Bulgarian morphology — adjective long-form definite article | 1b.3 (stemmer milestone) | Low | Backlog | `index.fts.bg_normalize()` strips last-character definite articles (`та/то/те/ят/ът`) only — symmetric across plural-definite ↔ plural-indefinite (D-022). Known asymmetry: adjective long-form definite (`новият` 6 chars → `нови` after stripping `ят`) does NOT match indefinite (`нов` 3 chars, below `_MIN_STEM_LEN=4`, returned unchanged). Same family: `българският`, `новият`, etc. Practical impact: legal text rarely surfaces these in subject position; queries like "обществените поръчки" already work. Phase 1b.3 evaluates a Snowball-style Bulgarian stemmer and synonym dictionary against real query logs (per D-022); this asymmetry is a candidate to fold in then. Test fixture for that milestone: `bg_normalize("новият") == bg_normalize("нов")` should pass after the stemmer lands. |
| FR-014 | Incremental index rebuild | 4 (consolidation engine) | Medium | Backlog | `index/build.py` currently does full DELETE-then-INSERT on every invocation (~45s for 3,573 acts). Phase 4's consolidation engine will produce per-amendment commits; re-indexing the entire catalog after each commit is wasteful. Add an incremental path that diffs git HEAD against `laws.current_commit` and re-indexes only the changed acts (re-parsing their .md and replacing their provisions/laws_fts rows). Keep the full-rebuild path as the operator escape hatch and the test-fixture-build mode. Watch out for FK invariants: when rebuilding only one act's rows, FTS5's auto-id remains correct because we DELETE + INSERT for that law_id. |
| FR-015 | Search ranking — synonym/abbreviation dictionary + rang-aware boost | 1b.3 (stemmer milestone) | Medium | Backlog | Phase 1b.1 search uses two-tier FTS5 + BM25 over `bg_normalize`-pre-processed text. Two known limitations needing the synonym/stemmer milestone: (a) Bulgarian abbreviations like `ЗОП` never appear in the parent law's title or body — Bulgarian laws don't self-reference by abbreviation — so `ЗОП` cannot resolve to `Закон за обществените поръчки` without a synonym dictionary. (b) For canonical title queries like "обществени поръчки" the parent law and its implementing regulation/registry/agency-правилник all match in title; current ranker puts ЗОП at #4, not #1. Add: a synonym map (ЗОП ↔ Закон за обществените поръчки, НК ↔ Наказателен кодекс, ГПК ↔ Граждански процесуален кодекс, …) AND a `rang`-aware re-ranking step that nudges parent laws above their implementing regulations when both match the same title query. Locked test: `bg_search_regression.yaml` includes `must_include` for the canonical phrase; promote to `must_top_3` after this lands and add the `ЗОП → ЗОП` case (currently removed because it needs the synonym dict). |
| FR-016 | Search performance — single-word category queries | 1b.2 (hard-budget milestone) | Medium | Backlog | Phase 1b.1 perf budget for `search` is 100ms p95 (soft); current implementation hits ~290ms p95 over the representative-query suite. The pathological case is single-word category queries like "наредба" (~477ms) which match all 2,604 ordinances by title — FTS5 has to rank them all to extract top-20. Two fixes to consider for 1b.2 (hard budgets): (a) stop-word list for category words (`наредба`, `закон`, `правилник`, `кодекс`, `постановление`) so single-word queries are rejected with a "be more specific" hint; (b) `BM25 + LIMIT pushdown` via FTS5's `rank` column / partial-evaluation paths. The other 9 representative queries already finish in <250ms; "наредба" alone is the budget-buster. |
| FR-017 | Search body snippet — currently title-only | 1b.3 (stemmer milestone) | Low | Backlog | Phase 1b.1's `search` returns highlighted-title snippets (FTS5 column 1) rather than body excerpts (column 2). The body-column `snippet()` cost ~700ms p95 because FTS5 must extract from the full indexed body (up to 559 KB for ЗОП); title snippets cost ~75ms. Title-snippet is informative for "which act is this?" and the model can call `get_law` for full body context one tool-call away. The 1b.3 redesign should evaluate: (a) storing a truncated body excerpt (first 5,000 chars) as a separate FTS5 column for snippet purposes; (b) Python-side snippet from a substring fetch on the largest matches. Either approach lifts the body-snippet cost to ~50ms while preserving full-body matching for ranking. |
