| FR-013 | Bulgarian morphology — adjective long-form definite article | 1b.3 (stemmer milestone) | Low | **Done (2026-05-09)** | **CLOSED in Phase 1b.3** via per-suffix MIN_STEM_LEN table in `index/fts.py:_BG_DEFINITE_SUFFIXES`. | FR-014 | Incremental index rebuild | 4 (consolidation engine) | Medium | Backlog | `index/build.py` currently does full DELETE-then-INSERT on every invocation (~45s for 3,573 acts). Phase 4's consolidation engine will produce per-amendment commits; re-indexing the entire catalog after each commit is wasteful. Keep the full-rebuild path as the operator escape hatch and the test-fixture-build mode. Watch out for FK invariants: when rebuilding only one act's rows, FTS5's auto-id remains correct because we DELETE + INSERT for that law_id. |
| FR-015 | Search ranking — synonym/abbreviation dictionary + rang-aware boost | 1b.3 (stemmer milestone) | Medium | **Done (2026-05-09)** | **CLOSED in Phase 1b.3** via two orthogonal layers: (a) hand-curated `index/synonyms.LEGAL_ABBREVIATIONS` (22 entries — ЗОП, НК, ГПК, КТ, etc.); `expand_if_abbreviation` rewrites single-token queries pre-FTS5; multi-word queries pass through unchanged. | FR-016 | Search performance — single-word category queries | 1b.2 (hard-budget milestone) | Medium | **Done (2026-05-09)** | **CLOSED in Phase 1b.2 via approach (a) — stop-word reject path raising new `QUERY_TOO_BROAD` error.** Implementation: `mcp_server/queries.py:full_text_search` tokenizes the query (alphanumeric runs only, ignoring punctuation), bg_normalize-s each token, and rejects when `len(tokens) == 1` AND the token is in `_CATEGORY_STOP_WORDS = {наредба, закон, правилник, кодекс, постановление}`. The reject runs in <0.1 ms (vs the original 437 ms cold-call FTS5 ranking over 2,604 ordinances). Resolved via DEFERRED.md row D-2026-05-09-03 → Implemented; D-028 captures the design choice (chose stop-word reject over BM25/LIMIT pushdown for smaller code + cleaner UX). Round-4 review caught a v1 bypass via punctuation suffixes (`наредба—`); fixed in commit `06195fa1` by tokenizing before bg_normalize. |
| FR-017 | Search body snippet — currently title-only | 1b.3 (stemmer milestone) | Low | **Done (2026-05-09)** | **CLOSED in Phase 1b.3** via opt-in body-snippet generation. New `include_body=False` parameter on `search`; when True, the top 2 hits get a Python-extracted ±60-char window around the first matching token in `laws_fts.body` with `<b>...</b>` highlighting. Empirical measurement on the live catalog ruled out the FR's optimistic "~50ms" estimate: even TOP_N=2 fetches cost ~150 ms because the largest indexed bodies are 1+ MB and SQLite materializes the full row regardless of `substr()`. The opt-in design preserves the 100 ms warm + 250 ms cold p95 budgets for default callers; callers that explicitly want body context pass `include_body=True` and accept the extra latency. New non-optional `body_snippet` field on `SearchHit` (additive per Surface 3); empty string when not requested or for results 3-N. See D-029. |
| FR-018 | `get_article` range expansion | 2 (or 1b.3 if usage demands it) | Low | Backlog | `mcp_server.queries.parse_article_spec` already accepts `чл. 14-16` and parses it as a range, but `mcp_server.server.get_article` returns only the row for `article=14` — the second and third articles in the range are silently dropped. Phase 1b.1 chose this rather than ship a partial range implementation that would interact awkwardly with `version_at_date` and the `valid_to` predicate. Future work: change `get_article` to return a `list[ArticleEntry]` when the spec parses to a range, OR add a separate `get_articles` tool that accepts a list of article numbers. Either path interacts with D-024's response shape and is therefore a contract change requiring preflight (Protected Surface 3 — MCP tool signatures). Test scaffold for that milestone: `parse_article_spec("чл. 14-16")` should expand to a list of 3 articles and the tool should return all three. |
| FR-019 | Cyrillic case-insensitive title resolution | 2 (surfaced) | Low | Backlog | `mcp_server.queries.resolve_name_to_law_id` step 3 matches titles via SQLite `LOWER(title) = LOWER(?)`, but SQLite's built-in `LOWER()` is ASCII-only and does not lowercase Cyrillic — so a mixed-case Cyrillic title lookup (e.g. `Закон за обществените поръчки` vs the all-caps stored `ЗАКОН ЗА ОБЩЕСТВЕНИТЕ ПОРЪЧКИ`) misses. The identificador (step 1) and exact-slug (step 2) paths are unaffected, so every act stays reachable by its stable handles; this only bites title lookups with a Cyrillic case mismatch. Surfaced during the Phase 2 smoke test (2026-06-21). Affects all name-resolving tools (`get_law`, `get_article`, `history`, `diff`). Candidate fix: case-fold in Python (`str.lower()` / `bg_normalize`) before the SQL query rather than relying on SQLite `LOWER()`. Pre-existing (predates Phase 2); not a regression. |
