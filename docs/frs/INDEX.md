| FR-017 | Search body snippet — currently title-only | 1b.3 (stemmer milestone) | Low | **Done (2026-05-09)** | **CLOSED in Phase 1b.3** via opt-in body-snippet generation. | FR-019 | Cyrillic case-insensitive title resolution | 2 (surfaced) | Low | **Done (2026-06-21)** | **CLOSED in batch 2.x-a** via a deterministic `pylower` UDF (`str.lower`, full-Unicode) registered by `queries.register_query_functions(conn)` — called in `build_app` (all tool paths) and the test `conn` fixture. | FR-020 | Multi-version `law_versions` from git history (enables temporal `diff` / historical `get_law(date)`) | 2.x follow-up (or 4) | Medium | Backlog | `index/build.py` writes exactly ONE `law_versions` row per act (`valid_from` = effective_date/fecha_publicacion, `commit_hash` = current HEAD), so `version_at_date` always resolves to a single commit: `diff(law, d1, d2)` returns the bilingual "single consolidated version held" note and `get_law(name, date)` returns current text for any date. This stays true even after the 2026-06 corpus re-scrape (D-030), which created per-act `[reforma]`/`[popravka]` git commits — those commits exist in git history but are never materialized into `law_versions` rows. **To enable real temporal diffs:** walk each act file's `git log` and INSERT one `law_versions` row per commit with `valid_from` = that commit's author-date (the legislative date), `commit_hash` = the commit, `valid_to` = the day before the next version's `valid_from` (NULL for the latest). Then `version_at_date(date)` resolves to the historical commit, `diff` runs a real `git diff`, and `history()` can carry a real `commit_hash` per entry instead of NULL. Interacts with §7.2 `date_uncertain` handling and the INCLUSIVE `valid_to` predicate (schema-reference §2). This is the "write-side accumulates more text versions" the D-031 honest-semantics note refers to. Overlaps but is simpler than FR-009 (historical reconstruction) — the commits already exist, so no reverse-application is needed, only a `git log`-driven population; pairs naturally with FR-014 (incremental rebuild). Surfaced 2026-06-21 when D-030 merged but `diff()` stayed single-version. |
| FR-021 | Proper Bulgarian Snowball stemmer for search recall | 2.x follow-up (its own eval-gated effort) | Medium | Backlog | **Deferred out of batch 2.x-a (D-032).** `index/fts.py:bg_normalize` strips only definite-article suffixes (per-suffix `MIN_STEM_LEN`, longest-first); the canonical open recall gap is `българският` (masc adjective, consonant stem) vs the indefinite `български`. The `ият` rule already strips `българският → българск`, but the **indefinite** form ends in bare `-и` and is left intact, so the two still diverge. Closing it requires stripping bare `-и`, which mangles plural nouns (`закони`, `поръчки`) and collides with the already-REJECTED `ия`/`ите` suffixes (`решения → реше`) — a genuine POS-aware morphology problem solvable only by a real stemmer. **Why not in 2.x-a:** (1) a stemmer lib (`snowballstemmer`/`PyStemmer`) conflicts with **D-022** (pure-Python, no external NLP libs) — superseding D-022 is owner-ratifiable, not a quiet default; (2) `bg_normalize` symmetry is load-bearing → any change forces a full re-index (~45 s) and risks the locked ranking behavior (two-tier title match, FR-015 synonym + rang-tier sort, FR-013 `новият→нов`); (3) it needs a full-corpus precision/recall **eval harness** before it can be trusted — a sub-project, not a batch item. **Scope when picked up:** decide D-022 disposition; build the eval harness (real query set, precision/recall); apply the stemmer symmetrically at index+query; full re-index; re-lock the ranking tests. Pairs with FR-014 (incremental rebuild) to cut re-index cost. Surfaced 2026-06-21 (batch 2.x-a scoping). |
